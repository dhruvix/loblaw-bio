# Loblaw Bio - Immune Cell Population Dashboard

Analysis pipeline and interactive dashboard for exploring immune cell population
counts across patients in a miraclib clinical trial.

## Running this project

Designed to run in GitHub Codespaces (or any machine with Python 3 and `make`).

```bash
make setup      # creates .venv and installs dependencies from requirements.txt
make pipeline   # builds cell-count.db (Part 1) and writes output/*.csv (Parts 2-4)
make dashboard  # starts the Streamlit dashboard
```

`make dashboard` serves on `http://localhost:8501`. In Codespaces, accept the
prompt to open the forwarded port, or open it from the "Ports" tab.

**Dashboard link:** `http://localhost:8501` for now (local). A public link will
be added here once it's hosted.

Each target only needs the previous one to have run once. Re-running `make setup`
or `make pipeline` is safe because both just overwrite what's already there.

## Repository structure

| File | Role |
|---|---|
| `cell-count.csv` | Raw input data provided for the assignment |
| `load_data.py` | Part 1. Builds the SQLite schema and loads the CSV into it |
| `analysis.py` | Parts 2-4. One function per question, plus a CLI entrypoint that runs all of them and writes `output/` |
| `dashboard.py` | Interactive Streamlit dashboard |
| `cell-count.db` | Generated SQLite database (checked in, and regenerated by `make pipeline`) |
| `output/` | Generated CSVs, one per analysis question (checked in, and regenerated by `make pipeline`) |
| `requirements.txt` | Python dependencies |
| `Makefile` | `setup` / `pipeline` / `dashboard` targets |

### Why it's structured this way

`load_data.py` does one thing: build the database from the CSV. It takes no
arguments and should be run to create and populate the database.

`analysis.py` has one function per question Bob asks. Each takes a
`sqlite3.Connection` and returns a plain `list[dict]`, with no pandas dependency
at this layer, so the SQL and stats logic is easy to read and test on its own.
A `QUESTIONS` dict maps a short key (`"2"`, `"3a"`, `"3b"`, `"3c"`, `"4a"`, `"4b"`)
to a description and a function, so the CLI can loop over all of them the same
way and write each result to `output/part_<key>.csv`. Adding a new question
later just means adding one function and one entry in that dict. I have more on why I added a `"3c"` below.

`dashboard.py` is presentation only. It imports `analysis.py` and queries the
live database through the same functions the CLI uses, instead of reading the
generated CSVs back in. That keeps one source of truth for the SQL and stats
logic, and it means the dashboard isn't stuck with only the exact slices that
got pre-computed if interactive filtering gets added later.

## Database schema

```
projects(
  project_id PK,
  project_name UNIQUE
)

subjects(
  subject_id PK,
  subject_code UNIQUE,
  project_id FK,
  condition,
  age,
  sex,
  treatment,
  response
)

samples(
  sample_id PK,
  sample_code UNIQUE,
  subject_id FK,
  sample_type,
  time_from_treatment_start
)

cell_counts(
  cell_count_id PK,
  sample_id FK,
  population,
  count,
  UNIQUE(sample_id, population)
)
```

**Normalized subject fields.** The raw CSV repeats subject-level fields
(`condition`, `age`, `sex`, `treatment`, `response`) on every sample row for that
subject. I checked and these are consistent per subject across all their
samples, so they live once on `subjects` instead of being duplicated on every
sample row.

**Long format for `cell_counts`.** Instead of five fixed columns
(`b_cell`, `cd8_t_cell`, and so on), each (sample, population) pair gets its own
row. That makes "filter or group by population" a normal `WHERE` / `GROUP BY`
instead of five separate column references, and adding a sixth population later
is just new rows, not a schema change.

**Surrogate integer primary keys.** `project`, `subject`, and `sample` in the
CSV are human-readable codes, not identifiers guaranteed to stay put. A code can
get renamed without the underlying project or patient changing. So each entity
gets its own auto-increment integer primary key, and the CSV's string code is
kept as a `UNIQUE` column alongside it. Foreign keys point at the surrogate
integer, so renaming a code never cascades into a primary key change elsewhere.

### How this scales

The current dataset (3 projects, 3,500 subjects, 10,500 samples, 52,500 cell
count rows) is already a large sample in
order of magnitude as it is, and this schema handles that fine as it stands. Past that
point, a few things would need to change:

- **Move from SQLite to a client-server database (Postgres, most likely).**
  SQLite is a single file with effectively one writer at a time, which is fine
  for a batch load plus a read-only dashboard, but not for several analysts
  running concurrent queries or writes against it. The schema itself is
  ordinary normalized SQL and moves to Postgres without a redesign.
- **Add indexes for the queries that actually get run.** Right now the indexes
  cover the foreign keys and `population`. Parts 3 and 4 both filter on the same
  combination (`condition`, `treatment`, `sample_type`,
  `time_from_treatment_start`), so a composite index on that combination, or on
  whatever filters turn out to be common across other analyses, would keep
  things fast as the tables grow.
- **A `populations` lookup table** (`population_id`, `name`, and so on) instead
  of the `CHECK` constraint on `cell_counts.population` would make sense if
  future analytics need metadata about a population, like parent lineage or
  panel version, rather than just its name.
- **A precomputed relative-frequency table**, if that calculation turns out to
  be a hot path across many different analyses. Right now it's computed on the
  fly with a window function on every query, which is cheap at this scale but
  would be worth caching if it's queried heavily across hundreds of projects.

## A note on Part 3

Part 3 asks for a comparison of responders vs. non-responders using all
qualifying PBMC samples. Taken literally, that pools each subject's three
visits (day 0, 7, 14) as if they were independent observations, but they're
not. They're repeated measures on the same person. Treating them as
independent inflates the effective sample size and biases the p-values toward
finding significance that isn't really there (a classic pseudoreplication
problem). This isn't something the assignment asked for and it's an extra check I
added on top of it.

`analysis.py` has both versions:

- **3b** (`responder_significance`), as specified, with all qualifying samples
  pooled.
- **3c** (`baseline_responder_significance`), restricted to baseline (day 0)
  samples only, so each subject contributes exactly one observation. This is
  also the more defensible way to frame "predicting response," since a
  predictive biomarker should be measured before the drug has had a chance to
  act on it. A day-14 measurement is at least partly a result of the response
  it's supposedly predicting.

Neither version finds a population that's significant once you correct for
testing all five populations at once (Benjamini-Hochberg FDR, alpha = 0.05). The dashboard only shows the data from 3b since that is what the assignment is asking.
