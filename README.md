# Loblaw Bio - Immune Cell Population Dashboard

Analysis pipeline and interactive dashboard for exploring immune cell population
counts across patients in a miraclib clinical trial.

## Running this project

Designed to run in GitHub Codespaces (or any machine with Python 3 and `make`).

```bash
make setup      # creates .venv and installs dependencies from requirements.txt
make pipeline   # builds cell-count.db (Part 1) and writes output/*.csv (Parts 2-4)
make dashboard  # starts the Streamlit dashboard
```

`make dashboard` serves on `http://localhost:8501` — in Codespaces, accept the
prompt to open the forwarded port (or open it from the "Ports" tab).

**Dashboard link:** `http://localhost:8501` (local for now — a public link will be
added here once hosted).

Each target only depends on the previous one having been run once; re-running
`make setup` or `make pipeline` is safe and idempotent.

## Repository structure

| File | Role |
|---|---|
| `cell-count.csv` | Raw input data provided for the assignment |
| `load_data.py` | Part 1 — builds the SQLite schema and loads the CSV into it |
| `analysis.py` | Parts 2-4 — one function per question, plus a CLI entrypoint that runs all of them and writes `output/` |
| `dashboard.py` | Interactive Streamlit dashboard |
| `cell-count.db` | Generated SQLite database (checked in; also regenerated by `make pipeline`) |
| `output/` | Generated CSVs, one per analysis question (checked in; also regenerated by `make pipeline`) |
| `requirements.txt` | Python dependencies |
| `Makefile` | `setup` / `pipeline` / `dashboard` targets |

### Why it's structured this way

`load_data.py` has a single responsibility — build the database from the CSV —
and takes no arguments, so it can be run identically by a human or a grader.

`analysis.py` holds one function per question Bob asks, each taking a
`sqlite3.Connection` and returning a plain `list[dict]` (no pandas dependency at
this layer, so the SQL/stats logic stays easy to read and unit-testable in
isolation). A `QUESTIONS` registry maps a short key (`"2"`, `"3a"`, `"3b"`, `"3c"`,
`"4a"`, `"4b"`) to `(description, function)`, so the CLI can loop over all of them
uniformly and write each to `output/part_<key>.csv` — adding a new question later
means adding one function and one registry entry, nothing else.

`dashboard.py` is presentation-only: it imports `analysis.py` and queries the
live database directly (through the same functions the CLI uses), rather than
reading the generated CSVs back in. That keeps a single source of truth for the
SQL/stats logic and means the dashboard isn't limited to pre-baked slices of data
if interactive filtering is added later.

## Database schema

```
projects(project_id PK, project_name UNIQUE)
subjects(subject_id PK, subject_code UNIQUE, project_id FK,
         condition, age, sex, treatment, response)
samples(sample_id PK, sample_code UNIQUE, subject_id FK,
        sample_type, time_from_treatment_start)
cell_counts(cell_count_id PK, sample_id FK,
            population CHECK(...), count,  UNIQUE(sample_id, population))
```

**Normalization:** the raw CSV repeats subject-level fields (`condition`, `age`,
`sex`, `treatment`, `response`) on every one of a subject's sample rows. These
were verified to be consistent per subject across all their samples, so they're
stored once on `subjects` rather than duplicated per sample.

**Long format for `cell_counts`:** rather than five fixed columns
(`b_cell`, `cd8_t_cell`, ...), each (sample, population) pair is its own row.
This makes "group/filter by population" a plain `WHERE`/`GROUP BY` instead of
five parallel column references, and adding a sixth population later is a data
change, not a schema migration.

**Surrogate integer primary keys:** `project`, `subject`, and `sample` in the CSV
are human-readable codes, not guaranteed-stable identifiers — a code can be
renamed without the underlying entity changing. Each entity gets its own
auto-increment integer PK, with the CSV's string code kept as a `UNIQUE` natural
key. Foreign keys point at the surrogate integer, so a code rename never cascades
into a primary-key change.

### How this scales

The current dataset (3 projects, 3,500 subjects, 10,500 samples, 52,500 cell
count rows) is already close to "hundreds of projects, thousands of samples" in
order of magnitude, and this schema handles that scale comfortably as-is. Beyond
that, a few things would need to change:

- **Move from SQLite to a client-server RDBMS (e.g. Postgres).** SQLite is a
  single-file, effectively single-writer database — fine for a batch load plus a
  read-only dashboard, but not for multiple analysts running concurrent queries
  or writes. The schema itself is standard normalized SQL and moves to Postgres
  with no redesign.
- **Add indexes matched to real query patterns.** The current indexes cover the
  foreign keys and `population`. In practice, Parts 3-4 repeatedly filter on the
  same combination (`condition`, `treatment`, `sample_type`,
  `time_from_treatment_start`) — a composite index on that combination (or on
  whatever filters turn out to be common across "various types of analytics")
  would keep those queries fast as `subjects`/`samples` grow.
- **Consider a `populations` lookup table** (`population_id`, `name`, ...) instead
  of the `CHECK` constraint on `cell_counts.population`, if future analytics need
  metadata about a population (parent lineage, markers, panel version) rather
  than just its name.
- **Consider a materialized view or precomputed table for relative frequency** if
  it becomes a hot path across many different analyses — right now it's computed
  on the fly with a window function per query, which is cheap at this scale but
  would be worth caching if queried very frequently across hundreds of projects.

## Statistical note on Part 3

The assignment's Part 3 asks to compare responders vs non-responders using all
qualifying PBMC samples. Doing that literally pools each subject's three visits
(day 0, 7, 14) as if they were independent observations, which they are not —
they're repeated measures on the same person, and treating them as independent
inflates the effective sample size and biases p-values toward false positives
(pseudoreplication). This isn't something the assignment asked for explicitly;
it's an additional check applied on top of it.

`analysis.py` includes both versions:

- **3b** (`responder_significance`) — as specified, all qualifying samples pooled.
- **3c** (`baseline_responder_significance`) — restricted to baseline (day 0)
  samples only, so each subject contributes exactly one independent observation.
  This is also the more defensible framing for "predicting response," since a
  predictive biomarker should be measured before the drug can have affected it —
  a day-14 measurement is at least partly a consequence of the response it's
  being used to "predict."

Neither version finds a population that's significant after correcting for
testing all five populations at once (Benjamini-Hochberg FDR, alpha = 0.05).
